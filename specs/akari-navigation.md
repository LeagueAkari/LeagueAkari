# Akari Navigation

## 目的

Akari Navigation 用来完成那些无法一步抵达的界面导航。

目标可能尚未渲染，也可能藏在页面、弹窗、标签页或其他按需创建的容器中。导航因此不应由一个拥有整棵 UI 和 DOM 视角的控制器强行完成，而应被描述成一条预先确定的路径，并由路径上的参与者逐层创造后继节点可以工作的条件。

这份 spec 描述的是导航方法论。具体状态容器、组件 API、进程通信方式和等待机制都可以替换，只要继续满足下述语义和约束。

## 核心模型

一次导航由四个概念组成：

- **Execution**：一次从开始到结束的导航执行，持有路径、当前位置、生命周期和取消信号。
- **Path**：按顺序排列的步骤。路径必须在导航开始前确定，并且能够真实地通向目标。
- **Cursor**：当前正等待或执行的步骤位置。它是 execution 唯一的推进状态。
- **Step**：路径上的一个接力节点，由全局唯一的 key 标识，并可以携带仅供该节点消费的 payload。

路径表达“依次需要谁”，而不表达“控制器应该怎样操作界面”。打开页面、显示弹窗、切换标签、加载数据、播放内容或滚动到目标，都由相应 step 所属的业务决定。

## 接力机制

导航严格按路径从上到下接力：

1. execution 从 cursor `0` 开始，只寻找当前 step 的处理者。未轮到的 step 不会被激活。
2. 如果处理者已经存在，立即调用它；如果目标 UI 尚未创建，则等待该处理者注册。注册本身就是“目标现在可以接棒”的信号。
3. 当前 step 根据自己的 payload 完成局部职责。它通常需要改变业务状态，例如打开容器、切换路由或标签、触发渲染，使下一个 step 有机会注册并可用。
4. step 只有在其职责已经完成、且下一层已经就绪或即将通过正常渲染周期就绪时，才可以报告 ready。仅仅发起异步操作不等于 ready；必须等待该操作真正创造出后继条件。
5. 当前 step ready 后，execution 才将 cursor 前移一位，然后以同样方式等待和激活下一棒。
6. 最末端 step 完成最终动作后结束 execution。设置项滚动只是一个典型终点；任何可完成的业务动作都可以成为终点。

因此，每个 step 同时是一道局部边界和一个中转站：它只理解自己这一层，不需要知道完整路径，也不直接驱动后代节点。

例如，一条路径可以表达为：

```text
主窗口 → 设置弹窗 → 存储标签页 → 标记的玩家
```

各棒的职责分别是：

```text
显示并等待弹窗可用
  → 选择并等待设置页签渲染
    → 选择并等待存储子页签渲染
      → 滚动并高亮最终目标
```

任何一棒都不应越过下一棒直接查找最终 DOM。否则路径的局部性会被破坏，隐藏的时序和组件结构耦合也会重新集中到基建中。

如果某个业务目标在当前状态下可能根本不会创建，就不能把一个永远不会注册的 step 留在路径中等待超时。目标所属的业务应通过始终可达的准备 step 明确返回 unavailable，或让 registry 直接把路径落到一个真实存在的替代终点，再由业务级 fallback 决定下一条路径。

## 必须保持的不变量

- 同一 execution 在任意时刻只激活或等待一个 step。
- 整个 Akari Navigation 命名空间中，step key 全局唯一；重复注册应立即暴露为错误。
- cursor 只在当前 step 确认 ready 后推进。
- path 必须预先确定，且每一步都对应真实可能出现的处理者。
- payload 属于当前 step；同一路径中不同 step 的 payload 可以完全不同，不存在隐式的逐步变形规则。
- execution 只共享导航生命周期、cursor、deadline 和取消状态。业务若需要额外上下文，应显式放入相应 payload，不能依赖隐藏的全局可变状态。
- 新导航可以取代旧导航。旧 execution 被取消后，其未完成异步任务不得继续提交会覆盖新导航的状态。
- deadline 属于整次 execution，而不是每一棒重新计时；等待注册和执行 handler 都消耗同一份时间预算。
- 不可用、失败、取消和超时是不同结果，不能被模糊成同一种“没有完成”。

## 基建与业务的边界

基建只负责：

- 保存当前 execution、path 和 cursor；
- 按 key 匹配 step 处理者；
- 保证串行接力；
- 管理注册等待、取消、超时和结果；
- 拒绝重复 key。

基建不理解页面、路由、弹窗、标签页、设置项、DOM 或动画。

业务负责：

- 定义 step key、payload 和 handler；
- 判断一次激活应该改变什么状态；
- 等待状态变化真正形成下一棒的接棒条件；
- 组装真实可达的路径；
- 在需要时提供业务级 fallback。

集中式 registry 可以拥有“上帝视角”，因为路径只有在同时了解入口、层级和终点时才能被正确组装。这个耦合是显式且可维护的业务耦合，不应下沉到通用运行时。业务特化也应留在其所有者附近，例如某个标签页如何切换，由该标签页自己处理，而不是由 registry 或基建代为操作。

## DOM 边界

导航过程应尽可能通过响应式状态和组件生命周期推进，避免基建直接查询或操纵 DOM。

最终目标有时必须执行 `scrollIntoView`、聚焦或播放等命令式动作。这样的 DOM 操作应被限制在最末端、由目标业务拥有的适配层中。上游 step 只负责让目标真实渲染和可用，不应持有目标元素。

## 跨窗口扩展

窗口边界不改变接力模型。未来跨窗口时，路径中的某一棒可以负责唤起或切换窗口，并把后续 execution 交给该窗口中的运行时；主进程可以协调生命周期、取消和结果回传。

无论传输层如何实现，仍必须维持同一条有序路径、单 cursor、共享 deadline 和逐棒 ready 的语义。跨窗口协调不应迫使 renderer 基建理解具体业务目标。
