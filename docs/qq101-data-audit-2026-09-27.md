# QQ101 数据接口审计（2026-09-27）

## 结论与范围

本次核对当前仓库的 QQ101 HTTP helper、协议适配器、renderer loader/controller，以及官网 20260924 构建的榜单和详情实现。对现有全部 17 个不同的远端接口进行了实时请求（`getLatestPatch` 与 `getPatches` 共用接口），另核对三个尚未接入的统计接口和三个资源目录。请求采用最多两个并发；没有改动生产代码、查询偏好或账号状态。

本报告是公开接口的观测结果，不是腾讯提供的稳定协议承诺。记录数量和统计日期仅代表此次采样；未枚举所有英雄、段位、版本和日期组合。

**目前不能把“正常返回数组”视为适配完成。至少存在正常空数据被当成协议错误、详情 ALL 分路失效、符文主系和排序错误、跨榜单日期丢失、资源目录缺项等已复现问题。**

## 1. 请求与响应约定

接口主机为 `https://mlol.qt.qq.com`。下表中统计接口统一省略 `/go/battle_info/odp_proxy/` 前缀。

- HTTP 200 不代表有数据，外层 `code: 0` 也不代表有数据。
- 统计接口通常返回 `data._fieldValues.Rxxxxx`，值是 JSON 字符串；**值为空字符串也是实际存在的正常无数据响应**。
- 内层 JSON 继续包含按 `#`、`_`、`|` 等分隔的记录。分隔符必须逐接口解释，不能通用地把所有标点视为可互换。
- 官网兼容 `data.result` 等外壳；本次实时统计接口主要为 `_fieldValues`。外壳兼容与记录 schema 校验需要分别处理。
- 版本列表直接返回 `data` 数组，不经过内层 JSON。
- 峡谷分路为大写 `ALL/TOP/JUNGLE/MIDDLE/BOTTOM/SUPPORT`；经典为小写 `all/top/jungle/middle/bottom/support`。应用内部 `utility` 需要转换。
- `itier` 是来源自己的编码，不应复用 OP.GG 的段位枚举。官网至少区分 255（全部）、88（峡谷之巅）、26（翡翠+），以及单段位与以上段位。

### 正常无数据与协议错误必须拆开

本次实测：

| 请求                             | 返回                | 当前适配器行为         |
| -------------------------------- | ------------------- | ---------------------- |
| 极地 `dtstatdate=20260927`       | `code=0, R6993=""`  | 抛出缺失 record string |
| 海克斯英雄 `dtstatdate=20260927` | `code=0, R15380=""` | 抛出缺失 record string |
| 峡谷不存在版本 `0.0`             | `code=0, R17960=""` | 抛出缺失 record string |
| 阿狸出装 `lane=ALL`              | `code=0, R18087=""` | 返回空 slots           |
| 阿狸符文 `lane=ALL`              | `code=0, R18119=""` | 返回空 pages           |

上一轮新增的 `rankingRecords` 校验把“还未发布数据”和“字段改名”合并成同一错误。应保留校验，但先在外壳层识别明确的空值。否则 loader 的“最新版本无数据时回退上一版”分支无法执行：它只处理成功结果中的空 champions。

建议统一保留三种结果：有数据、明确无数据、解析失败。网络错误和取消另行处理。不要为了回退，把所有异常都吞掉。

### 峡谷

11 列依次是：分路内排名、英雄 ID、T 级、分路、胜率、登场率、禁用率、反制英雄 ID 列表、排名变化、热度相关数值、热度标记。最后两列在官网分别以 `daily_avg_surge`、`is_hot` 使用，目前适配器未保留；数值的业务定义尚未从独立协议确认，不宜自行命名成“胜率增幅”。

- 本次全部榜 218 行，仅 169 个不同英雄、51 个不同 rank；英雄和 rank 都不唯一。行标识至少由英雄 ID 和分路共同组成。
- “全部”不是把不同分路合并后的英雄总榜。不要把返回的第一行匹配当作这个英雄唯一摘要。
- 三种百分比是百分数文本，例如 `52.15` 应解析为 `0.5215`。
- 全部榜的默认显示顺序与服务端原始记录顺序不是完全相同的概念；UI 需明确排序键，不能直接用数组下标代替上游 rank。
- `16.19` 的响应统计日仍为 25 日；版本不是日期。

### 经典

7 列为排名、经典英雄 ID、胜率、登场率、禁用率、T 级、排名变化。

- 一个响应包含 `winrate_top_hero_list`、`bannedrate_top_hero_list`、`pickrate_top_hero_list`、`tierscore_top_hero_list`。当前只保留 T 级排序列表。改排序时可本地排序，但不要声称其他列表的独立排名变化也已经保留。
- 经典 ID 为 `60xxx`；官网使用独立 Jade 资源目录和 `Jade_*` alias。当前减 60000 适合关联普通英雄，但**不应该丢掉原始经典 ID**，否则后续经典头像、技能、出装资源会找错。
- “全部”的行没有具体分路字段。官网还用 `jade_hero_lane` 获取一个英雄的多个分路，不能用普通英雄的职业标签替代。
- 今日 26 日数据已更新；默认请求没有版本或日期参数，不能把它伪装成与峡谷版本绑定的数据。

### 极地 / 海克斯英雄

共用前 10 列：英雄 ID、排名、中文排名变化、胜率、登场率、前 50 搭档、平均死亡相关时间、参团比例、伤害占比、承伤占比。第 6 列再按 `&` 分搭档、`,` 分四项（ID、登场比例、胜率、rank）。海克斯额外第 11 列是强化 ID 列表。

- 本次上游返回的胜率等已经是 0–1 比例，不能再次除以 100。
- `未变化/上升N位/下降N位` 与数字排名变化是不同编码。缺失变化文本不等于已确认“未变化”。
- 第 7 列官网命名为 `avg_death_time`。当前适配器命名为 `averageDeathTimeSeconds`；其准确业务口径和单位未获得独立确认，一期榜单不展示该指标，避免擅自解释为“每次复活等待时间”。
- 英雄职业类别来自英雄资源目录，统计记录本身不含这些标签。
- 日期由请求指定，内层没有响应日期回显；应保留“请求日期”这一事实，而非制造“服务端确认日期”。

### 海克斯英雄的 T 级是派生数据

官网依据各职业内排名人数计算 T0–T4，边界为 `round(total * 4% / 15% / 30% / 40%)`，最低边界至少 1；后续边界不低于前一个边界。综合展示取该英雄各职业中的最佳 T 级，没有职业时再用全榜排名计算。

切换职业时显示对应职业 T 级，因此这不只是普通筛选。该逻辑应属于 QQ101 的 UI 数据投影，不应让协议适配器输出一个伪装成上游字段的固定 tier。

### 强化榜

9 列为强化 ID、查询品质标记、选取率、选取排名、选取排名变化、胜率、胜率排名、胜率排名变化、适配英雄列表。

- 全品质请求第二列为 255，不是实际品质；从 `kiwi_augments.json` 的 `level` 取银/金/棱彩。
- 官网对强化排名变化采用**负数上升、正数下降**；海克斯英雄中文排名变化转数字后则是正数上升。当前 DTO 没有说明这一区别，直接复用箭头组件会反向。建议保留 raw delta，再给 UI 统一的方向字段。
- 胜率排序显示 winRank，选取率排序显示 pickRank，对应变化也要同步切换。
- 本次统计含 ID `1379`，同期资源目录没有该项。必须保留该行，使用未知名称/占位图；不要依赖资源查找成功才能展示统计。
- `getMayhemAugments(date)` 的 date **没有发送给服务器**；它当前只用于响应缺日期时兜底。这个接口是当前快照，不是历史日期查询。

### 拍档榜

5 列：两个英雄 ID（`;`）、两个职业列表（`;` 分英雄、`,` 分职业）、配合胜率、登场率、排名。目前职业列被丢弃。

- 全局结果只有 2000 行，不是所有英雄组合的完整矩阵。
- `championid=103` 返回 39 行；首行 rank=415。这是筛选后仍保留的全局 rank，不能假定从 1 连续开始。
- 推荐以无序英雄对作为去重身份，但须保留原始顺序以便对齐职业列；是否所有时间窗口都保证无序唯一尚未穷举验证。
- 官方参数有 `role1/role2`，当前页面不暴露职业组合选择，helper 固定 255。以后新增筛选不能仅凭参数名猜测编码，需实际核对。

### 详情分路选择是当前加载链路的阻塞点

`loadDetails` 从 overview 按 championId 找第一行，之后仍把全局 `preferences.position` 用于全部详情请求。全局选择“全部”时会发送 `lane=ALL`。

实测阿狸 `ALL` 出装和符文为空；`MIDDLE` 有数据。阿狸 `TOP` 也有出装数据，而当前热门榜不一定列出她的这个分路。因此还存在第二个问题：**不能把“没有进入榜单”直接解释为“该英雄没有详情数据”**。

需要区分榜单位置过滤和英雄详情实际分路。从榜单行进入时携带该行分路；从其他入口进入时先加载可用分路，再确定详情分路。不能通过偷偷把所有 ALL 改成中路或上路解决。

### 符文错误已复现

- 阿狸12个符文页原始顺序为 `10,11,12,1,2...9`。当前适配器不排序，首项是选择率1.08%的 rank10；真正 rank1 为40.43%。
- rank2 基石为 `8992`，当前数字范围推断输出 `primaryStyleId=null`。官网目录确认它在巫术8200下，名称为冥火之触。
- 另一个已知范围外基石 `9923`（丛刃）属于主宰8100，也不受当前范围映射覆盖。
- 官网通过资源目录解析主系；副系还支持 `zj` 与 `zz` 两个别名，当前只支持 `zz`。
- 不应推断“所有未知基石都是某个默认主系”，也不应传不完整符文页给未来推荐应用逻辑。
- 单符文统计包含属性碎片位置：同 ID 可出现在不同槽位，不能只按 runeId 合并。

### 加点的特殊英雄

实测阿狸、杰斯、厄斐琉斯、乌迪尔均返回15项升级序列。杰斯、乌迪尔不符合普通英雄 QWE5级/R3级的模型；厄斐琉斯还涉及属性加点语义。

官网会对主序列补到18级，但这是显示推断，并非上游原始数据，不能照搬为可靠推荐。建议先原样保留 raw ability code 和完整返回序列长度，再在英雄资源和 UI 层解释；不能擅自补齐可执行加点计划。

### `fuwen_hero_rank?championid=103` — 海克斯英雄详情

## 6. 日期、空值与并发的跨接口问题

1. 当前 loader 用用户机器本地时区计算昨天，没有明确数据源的日界线。需要明确采用的时区；发布延迟时允许有限回退，并展示实际使用日期。
2. 今日实测英雄/强化/经典已到26日，拍档/部分详情/峡谷仍是25日。当前 `overview.data.date` 仅取英雄日期，丢弃强化和拍档日期。
3. 当前 `getMayhemAugments(date)` 与拍档接口不是日期受控请求；不能声称回退英雄日期后其余数据也同步回退。
4. 排位自动版本回退目前只处理空数组；严格记录校验会提前抛错。无数据、网络异常、格式错误应有不同路径。
5. 当前 QQ101 为单详情状态；选择英雄会重新加载 overview；详情10个请求一次 `Promise.allSettled`。未来多tab不能直接按tab数量放大成200个同时请求。
6. 现有 generation 和 AbortSignal 可防迟到结果覆盖，但没有每个详情模块的显式错误状态；`null` 混合了失败和缺数据，需要在 UI 接入前定义。

## 7. 解析器稳健性：现状与建议

已用本地构造输入复现（这些不是声称线上正在返回的异常）：

- 截断榜单记录 `1_103` 被接受成英雄103，位置为NONE、各统计为null，不能识别列数漂移。
- 出装字段改名后，解析器返回成功的六个空数组，和正常无数据不可区分。
- 指定 R 字段缺失但只有一个其他字段时，仍使用这个未知字段；这是有限兼容，但不等于验证了新版本 schema。
- 解析数字仅检查有限数值；没有验证 ID 为正整数、比例范围、列数、符文槽位数量等业务结构。不能因为 TypeScript 有类型就假定远端数据符合。

建议按接口定义最少必要约束，允许尾部新增字段而不允许核心列静默错位。无效单行可明确计数并隔离，但全量失败不能变成“暂无数据”。保留原始ID、来源字段和解析诊断，方便未来动态解析器保持相同输出契约。

不建议现在做脚本热更新或通用DSL；先明确输入版本、空数据语义、输出 DTO 和各接口不变量，未来即使动态下发也必须通过这些约束。
