# 批量购买英雄接口调研与实现方案

当前国服客户端的 LCU 购买接口已经完成一次真实成交验证。批量购买功能可以建立在逐名串行购买上，每名英雄购买后核对库存，再执行下一名。一次请求提交多名英雄的批次上限和部分失败行为仍未确定，首版不需要依赖这条路径。

## 实测范围与成交结果

采样时间为 2026 年 10 月 17 日 15:09 至 15:10，中国标准时间。客户端为 Windows 国服 `16.20.824.8524`。这些价格和库存只代表本次账号与地区的实时快照；其他地区通过同一组 LCU 接口检查能力和报价。

| 检查项           | 实测结果                                    |
| ---------------- | ------------------------------------------- |
| 试购英雄         | 北地之怒 瑟庄妮，`itemId: 113`              |
| 支付币种         | `IP`，即蓝色精萃                            |
| 支付价格         | 225 蓝色精萃                                |
| 购买响应         | HTTP 200，一条对应英雄的 transaction        |
| 确认模式         | `useRMSConfirmation: false`                 |
| 蓝色精萃余额     | 20,813 → 20,588，减少 225                   |
| 永久库存         | 新增且仅新增 `113`，`owned: true`           |
| 再次查询购买条件 | `item.owned: true`，`validation.item.owned` |
| 对局状态         | 购买前后均为 `InProgress`                   |

本次只购买了这一名英雄。后续对其余候选英雄的检查均为查询。

本机原始证据位于 `.playwright-mcp/pengu-purchase-research/`，该目录由 Git 忽略：

- `purchase-test-20261017.json`：购买请求、响应、前后余额与库存、全部单项查询结果。
- `eligible-champions-20261017.json`：试购后可购买英雄的 ID、名称和价格清单。
- `native-paw-excerpts.txt`：当前客户端原生购买封装及余额计算逻辑摘录。
- `evidence.json`：前一轮接口契约快照，余额和候选数量以本轮试购后记录为准。

## 可购买英雄

当前商店目录有 173 名标准英雄。试购后，将目录的 `itemId` 与永久库存匹配，得到 104 名未拥有英雄；逐个查询这 104 名英雄的购买条件，均返回 HTTP 200、有效的 `IP` 报价和空 `validationErrors`。每名英雄的单价均低于当前余额，但不能同时买下全部英雄。

| 单价 蓝色精萃 | 数量 | 合计 蓝色精萃 |
| ------------- | ---- | ------------- |
| 225           | 9    | 2,025         |
| 675           | 19   | 12,825        |
| 1,575         | 27   | 42,525        |
| 2,400         | 38   | 91,200        |
| 3,150         | 11   | 34,650        |
| 合计          | 104  | 183,225       |

225 档剩余英雄为提莫、沃里克、阿木木、蒙多医生、娑娜、波比、蕾欧娜、拉克丝、黛安娜。完整清单见本机 `eligible-champions-20261017.json`。

按单价升序、相同价格按英雄 ID 升序，当前 20,588 蓝色精萃可覆盖 31 名英雄：9 名 225 档、19 名 675 档，以及奥拉夫、加里奥、厄加特这 3 名 1,575 档。合计 19,575，剩余 1,013。这只是预算预览，不是默认购买清单。

候选英雄应从商店目录按 ID 与库存做差集，不能用两个数组的长度相减。当前库存包含不在标准英雄商店目录中的条目，例如 `600xx` ID。免费轮换、租用和临时权益也不能直接当作永久拥有。

## LCU 请求契约

API 声明来自当前客户端 `GET /Help?format=Full`，实际请求通过 Akari 现有的 LCU 连接完成。

| 用途             | 请求                                                                             | 实测结论                                                        |
| ---------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 商店状态         | `GET /lol-store/v1/store-ready`                                                  | HTTP 200，返回 `true`                                           |
| 英雄目录         | `GET /lol-store/v1/catalog?inventoryType=["CHAMPION"]`                           | HTTP 200，返回 173 项                                           |
| 永久英雄库存     | `GET /lol-inventory/v2/inventory/CHAMPION`                                       | HTTP 200，购买后新增对应 ID                                     |
| 蓝色精萃余额     | `GET /lol-inventory/v1/wallet/lol_blue_essence`                                  | HTTP 200，余额字段为 `lol_blue_essence`                         |
| 单项价格与条件   | `GET /lol-purchase-widget/v1/purchasable-item?inventoryType=CHAMPION&itemId=113` | 返回名称、拥有状态、价格和校验错误                              |
| 批量查询购买选项 | `POST /lol-purchase-widget/v1/purchasable-items/CHAMPION`，body 为英雄 ID 数组   | HTTP 200，但 choices 中的 item 和购买选项为空，首版采用单项查询 |
| 提交购买         | `POST /lol-purchase-widget/v2/purchaseItems`                                     | 单英雄真实成交已验证                                            |

购买请求如下。`items` 在契约中是数组，首版每次只放一名英雄；每次使用新查询得到的 `itemKey` 和报价。

```json
{
  "items": [
    {
      "itemKey": {
        "inventoryType": "CHAMPION",
        "itemId": 113,
        "subInventoryType": ""
      },
      "quantity": 1,
      "source": "collections",
      "purchaseCurrencyInfo": {
        "currencyType": "IP",
        "price": 225,
        "purchasable": true
      }
    }
  ]
}
```

`IP` 是购买报价和购买请求使用的蓝色精萃币种；余额查询使用 `lol_blue_essence`。不要把余额字段名直接替换进购买请求。

当前原生前端 `rcp-fe-lol-paw` 的内部服务 `purchaseWidgetService.purchaseItem(option, source, sectionId)` 使用同一请求。插件公开 API 主要负责打开购买弹窗，Akari 实现时直接使用 LCU。

单项查询的 `price.purchasable` 在本次未拥有英雄中为 `false`，但瑟庄妮真实购买成功。原生前端自己根据钱包计算能否支付，并在提交时构造 `purchasable: true`。候选判断因此应使用永久拥有状态、`validationErrors`、有效的 `IP` 报价和余额；不能单独据此标志禁用全部英雄。不要因为这个观测而忽略其他校验错误。

成功响应包含 `items`、`transactions` 和 `useRMSConfirmation`。本次为 `false` 且库存立即更新。原生前端在该字段为 `true` 时等待订单通知；实现需要处理这种确认方式，并在确认超时后标记结果待核对。

## 首版功能方案

### 页面与操作

在工具集中新增“购买英雄”页签，复用已有的 `TabbedPage`、`SettingsSection`、Naive UI 表格和主题样式。页面展示英雄头像、名称、蓝色精萃价格、勾选状态及购买结果，支持搜索、按价格排序、勾选和预算预览。

第一版只支持蓝色精萃。选择项没有 `IP` 报价时不可购买，不自动改用 `RP`。购买前展示选中英雄数量、总价、余额和预计剩余余额；价格发生变化时重新计算预览。用户可停止后续购买，已完成的购买保留结果。

### 数据加载

1. 查询商店状态、目录、库存和余额，按标准商店 ID 形成未拥有候选列表。
2. 从目录展示价格；为选中英雄逐项查询购买条件，查询最多 3 个并发。
3. 使用单项接口的实际 `IP` 报价计算总价，排除已拥有、不可售、缺报价或存在校验错误的项。
4. 预览绑定当前登录会话、地区和账号。断连、切换账号或地区后作废预览和选中项，重新加载。

### 购买执行

主进程持有一个串行执行队列。界面切换不销毁队列，重复点击或多个窗口不能创建重叠的购买任务。

每名英雄执行前，重新核对账号、永久拥有状态、购买条件、价格和余额。发现已拥有则跳过；报价变化或余额不足时停止并更新预览。预算以用户确认的总额和服务端实时报价约束，不能信任 renderer 传来的价格。

每次提交一个 `items` 元素，记录英雄 ID、币种、价格和交易标识。完成后查询永久库存，刷新余额，更新该项结果，然后进入下一项。响应不完整、断连或超时时先核对库存和订单状态，保留“待核对”结果，不自动重发购买。

停止操作只阻止下一项开始。已经提交的购买先完成结果核对，避免取消网络请求后丢失真实成交状态。连接或账号变化时停止任务，不自动在新账号上恢复。

### HTTP 重试边界

现有 main 和 renderer 的 LCU Axios 实例均安装了 `axios-retry`，配置为最多重试 2 次。当前依赖的默认条件包括网络错误，POST 也可能命中该分支。购买请求必须在实际发往 LCU 的 Axios 配置中设置：

```ts
{
  'axios-retry': { retries: 0 }
}
```

renderer 通过 IPC 发起购买任务，主进程直接调用购买 helper，避免经过两层 HTTP 重试配置。读取请求仍可保留现有重试策略。不能仅因一次请求抛错就把该英雄重新入队。

## 仓库接入位置

现有 `StoreHttpApi` 只有礼物好友查询，没有英雄购买封装；仓库中也没有批量购买英雄页面或执行模块。

| 层            | 建议接入                                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| LCU helper    | 扩充 `src/shared/http-api-axios-helper/league-client/store.ts` 的目录查询；新增 inventory 与 purchase-widget 的领域 helper，并注册到 `index.ts`   |
| 协议类型      | `src/shared/types/league-client/` 下添加实际使用的库存、购买选项、请求和响应类型                                                                  |
| 主进程        | 新建 `src/main/shards/champion-purchase/`；entry 只负责 DI、状态同步与生命周期，loader 负责读取，executor 负责串行购买及核对，IPC handlers 薄转发 |
| Renderer 状态 | 新建 `src/renderer-shared/shards/champion-purchase/`，同步候选、任务进度与结果，提供刷新、预览、开始和停止调用                                    |
| 工具集页面    | `src/renderer/src-main-window/views/toolkit/champion-purchase/`，在 `Toolkit.vue` 注册页签                                                        |
| 注册与文案    | main bootstrap、main window shard manager，以及中英文 toolkit 文案                                                                                |

现有 `background-tasks` 只有 renderer store，可作为进度展示入口；它不提供主进程购买队列、并发互斥或成交核对能力。

此功能查询和购买当前本地客户端账号，数据源使用 LCU。Pengu/CDP 用于本次调研，用户使用正式功能时不需要开启 CDP。首版不接入 SGP 或远端商店直连。

## 验收重点

- 单元与集成测试覆盖真实购买流程中的永久拥有过滤、价格与预算变化、无 IP 报价时拒绝购买、网络错误不重复提交、账号切换、停止后不执行下一项，以及确认超时后的待核对状态。
- 原生 LCU 联调检查提交、交易响应、库存和余额四者一致。mock 返回 HTTP 200 不能代替成交验证。
- renderer 使用真实 dev 窗口检查搜索、勾选、预算预览、进度、停止和结果刷新；不使用源码字符串断言证明交互。
- 本轮单英雄成交已通过。多项一次提交的数量上限、原子性、部分成功结构，以及其他地区的实际成交仍未建立，首版通过串行单项购买避免依赖这些未知契约。

实现阶段不应增加“启动后自动继续购买”或断连后自动重试成交的行为。
